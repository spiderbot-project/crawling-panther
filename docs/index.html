Power and signal

Eight servos draw far more current than the Arduino's own 5 V pin can supply. So the battery feeds a 5 V regulator through a switch, and the regulator powers two things: the servo rail on the shield, and the Arduino through the regulator's USB port. The Arduino only sends the control signals. When all servos start at once the supply dips, which is why the sketches start them one by one.

Software

Calibration

Servo horns never sit at exactly the same angle, so 90° is a different pose on every leg. We calibrated each servo by hand:

  1. Power the servos from the battery and send each one a test angle.
  2. Adjust until the leg stands neutral: hip pointing straight out, knee at its resting height.
  3. Write that angle into the neutral table shown in the servo map.
  4. Describe every movement as an offset from the neutral angle, never as an absolute angle.

Trot gait

The legs move as two diagonal pairs, R1 + L2 and R2 + L1. While one pair steps, the other stays on the ground and pushes the body forward. In gait v1 the hips swing 20° and the knees lift 45°. Every move is split into 20 small sub-steps so the servos glide instead of jumping.

In gait v1, one full step is six moves:

  1. Lift the knees of R3 and L4.
  2. Swing R1 and L2 forward, and R2 and L1 back.
  3. Lower the knees of R3 and L4.
  4. Lift the knees of R4 and L3.
  5. Swing R2 and L1 forward, and R1 and L2 back.
  6. Lower the knees of R4 and L3.

The v1 test routine does five steps forward, rests in the neutral pose, then does five steps backward.

#include <Servo.h>

enum { R1, R2, R3, R4, L1, L2, L3, L4, N };

const int pins[N]    = {4,   6,   5,   7,  8,   10, 9,  11};
const int neutral[N] = {85, 110, 170, 30, 110, 40, 70, 145};  // calibrated angles
const int sign[N]    = {1,   1,  -1,   1, -1,  -1,  1,  -1};  // mounting direction

const int HIP_SWING     = 20;
const int KNEE_LIFT     = 45;
const int STEPS         = 5;    // steps forward, then backward
const int INTERP_STEPS  = 20;   // sub-steps per movement
const int STEP_DELAY    = 12;   // ms between sub-steps

// If the robot walks backward instead of forward, swap these two values
const int FORWARD  =  1;
const int BACKWARD = -1;

Servo servos[N];
int cur[N];      // current angles
int target[N];   // target angles
int moveDir = FORWARD;

// Move all servos smoothly from cur[] to target[]
void apply() {
  int start[N];
  for (int i = 0; i < N; i++) start[i] = cur[i];
  for (int s = 1; s <= INTERP_STEPS; s++) {
    for (int i = 0; i < N; i++) {
      cur[i] = start[i] + (long)(target[i] - start[i]) * s / INTERP_STEPS;
      servos[i].write(cur[i]);
    }
    delay(STEP_DELAY);
  }
}

void hip(int i, int d) {
  target[i] = neutral[i] + sign[i] * HIP_SWING * d * moveDir;
}

void knee(int i, bool lifted) {
  target[i] = neutral[i] + (lifted ? sign[i] * KNEE_LIFT : 0);
}

// One full step: both diagonal groups move once
void gaitStep() {
  // Group R1+L2
  knee(R3, true); knee(L4, true); apply();                              // lift
  hip(R1, +1); hip(L2, +1); hip(R2, -1); hip(L1, -1); apply();           // swing
  knee(R3, false); knee(L4, false); apply();                           // lower

  // Group R2+L1
  knee(R4, true); knee(L3, true); apply();
  hip(R2, +1); hip(L1, +1); hip(R1, -1); hip(L2, -1); apply();
  knee(R4, false); knee(L3, false); apply();
}

void rest() {
  for (int i = 0; i < N; i++) target[i] = neutral[i];
  apply();
}

void setup() {
  for (int i = 0; i < N; i++) {
    cur[i] = target[i] = neutral[i];
    servos[i].write(cur[i]);
    servos[i].attach(pins[i]);
    delay(500);   // start servos one by one (protects the regulator)
  }
  delay(2000);    // wait 2 s before walking
}

void loop() {
  moveDir = FORWARD;
  for (int k = 0; k < STEPS; k++) gaitStep();
  rest();
  delay(1000);

  moveDir = BACKWARD;
  for (int k = 0; k < STEPS; k++) gaitStep();
  rest();
  delay(1000);
}
// crawling-panther: trot gait v2 (parameters learned in simulation), walks forward only.
// Same structure as v1; differences:
//   * left and right hips swing by different amounts (found by simulation)
//   * knee lift and hip swing happen together, then the knees come down (4 moves per cycle)
//   * slower than the simulation on purpose (STEP_DELAY)
#include <Servo.h>

enum { R1, R2, R3, R4, L1, L2, L3, L4, N };

const int pins[N]    = {4,   6,   5,   7,  8,   10, 9,  11};
const int neutral[N] = {85, 110, 170, 30, 110, 40, 70, 145};  // calibrated angles
const int sign[N]    = {1,   1,  -1,   1, -1,  -1,  1,  -1};  // mounting direction

// Learned in simulation (simulation/best_gait_v2.json): right 17.4, left 24.8, knee 45
const int HIP_SWING_R  = 17;
const int HIP_SWING_L  = 25;
const int KNEE_LIFT    = 45;

const int INTERP_STEPS = 22;    // sub-steps per movement (same as simulation)
const int STEP_DELAY   = 8;     // ms between sub-steps (simulation is ~4 ms; 8 ms = about half speed)

// If the robot walks backward instead of forward, change to -1
const int FORWARD = 1;

Servo servos[N];
int cur[N];      // current angles
int target[N];   // target angles

// Move all servos smoothly from cur[] to target[]
void apply() {
  int start[N];
  for (int i = 0; i < N; i++) start[i] = cur[i];
  for (int s = 1; s <= INTERP_STEPS; s++) {
    for (int i = 0; i < N; i++) {
      cur[i] = start[i] + (long)(target[i] - start[i]) * s / INTERP_STEPS;
      servos[i].write(cur[i]);
    }
    delay(STEP_DELAY);
  }
}

// d = +1 swings the leg forward, d = -1 backward
void hip(int i, int d) {
  int swing = (i == R1 || i == R2) ? HIP_SWING_R : HIP_SWING_L;
  target[i] = neutral[i] + sign[i] * swing * d * FORWARD;
}

void knee(int i, bool lifted) {
  target[i] = neutral[i] + (lifted ? sign[i] * KNEE_LIFT : 0);
}

// One full cycle: both diagonal groups move once
void gaitCycle() {
  // Group R1+L2: lift knees R3, L4 while R1, L2 swing forward and R2, L1 push back
  knee(R3, true); knee(L4, true);
  hip(R1, +1); hip(L2, +1); hip(R2, -1); hip(L1, -1);
  apply();
  knee(R3, false); knee(L4, false); apply();

  // Group R2+L1: lift knees R4, L3 while R2, L1 swing forward and R1, L2 push back
  knee(R4, true); knee(L3, true);
  hip(R2, +1); hip(L1, +1); hip(R1, -1); hip(L2, -1);
  apply();
  knee(R4, false); knee(L3, false); apply();
}

void setup() {
  for (int i = 0; i < N; i++) {
    cur[i] = target[i] = neutral[i];
    servos[i].write(cur[i]);
    servos[i].attach(pins[i]);
    delay(500);   // start servos one by one (protects the regulator)
  }
  delay(2000);    // wait 2 s before walking
}

void loop() {
  gaitCycle();    // walks forward until powered off
}

Robot model

The robot is described in a URDF file: a body, four hips and four legs, joined by eight revolute joints. Each joint is limited like an MG90S servo: 0.2 N·m of torque, 8 rad/s and a range of ±1 rad. The model weighs 342 g in total.

crawling-panther_v1.urdf is Rodi's first model. crawling-panther_v2.urdf is the corrected one, with the right weight, the servo limits and a fix for the root mass (see Challenges).

The physics engine is PyBullet. Floor friction and motor strength are estimates, so the simulation shows what is plausible, not what the real robot will do.

How the gait was learned

We used an evolutionary search. It needs no extra libraries and runs in a few minutes.

  1. A candidate gait is six numbers: right and left hip swing, right and left knee lift, speed, and a heading-correction gain.
  2. Every candidate walks 40 cycles in PyBullet.
  3. It receives a score (below).
  4. The five best candidates of a generation are averaged. The next 20 candidates are random variations around that average, and the variation shrinks a little each generation.
  5. This repeats for 25 generations of 20 candidates, which is 500 walks.
score = forward distance (cm) − sideways drift (cm) − 0.3 × heading change (°) − 60 if the body tilts more than 35°

The search ranges were chosen to suit the real robot: hip swing 5° to 25°, knee lift 20° to 45°, 15 to 60 sub-steps per move, gain 0 to 1.5. Bigger swings make the legs collide, and the MG90S knee is limited.

What it learned

The search ends with six numbers. The table shows each one next to the number that went into sketch v2. They differ slightly for two reasons. The search uses decimals, but an Arduino servo only moves in whole degrees, so the values are rounded. And the sketch waits 8 ms between sub-steps while the simulation steps every 4 ms, so on the real robot the gait runs at about half the simulated speed.

Heading correction

A walking robot drifts off its line. The correction works like a gyroscope loop: when the heading error grows, the stride on one side gets longer and on the other side shorter, in proportion to the error. The strength of the correction is the learned gain.

In the simulation the heading comes straight from the physics engine. The MPU6050 gyroscope is already mounted on the robot, but sketch v2 does not read it yet, so it walks without any correction.

Cross-check in Gazebo Experimental

We also load the same URDF into Gazebo to check the PyBullet result. The gait runs without feedback there, and the robot still tips over. We treat Gazebo as experimental and do not use its results.

Challenges

What went wrong, and what we know so far.

On the robot

Regulator protection

The voltage regulator went into protection and blinked when all 8 servos started at once. We now start the servos one at a time in code and added a power switch. The regulator module has its own capacitors that smooth the supply.

Fixed

Servo on pin 11

This servo (L4) sometimes does not respond. We suspect a power drop or a loose connector, but haven't confirmed it.

Open

Limited torque

The MG90S has little torque for a 342 g robot, so the gait needs careful tuning of angles and timing. Small changes decide whether a step lifts the body or stalls.

Managed by tuning

In the simulation

A heavy root link

PyBullet gave the first (root) link of the URDF a default mass of 1 kg. On top of the robot's 342 g, the model looked about four times too heavy, and its servos could not lift the legs. We added a tiny root mass (0.1 g) to the URDF, which fixed it. Lesson: add up the masses the simulator really uses and compare them with the scale.

Fixed

A gait that looked good for 15 cycles

Our first learning runs scored every candidate on 15 cycles. The winner looked good for 15 cycles, then started to turn, because its small heading error kept adding up. A short test rewarded gaits that only look good briefly. We made the test 40 cycles long and turned the heading-correction gain into a learned parameter.

Fixed in simulation

Different servo directions

In the simulation, each joint turns in the direction set by the URDF. On the real robot, the direction depends on how each servo horn was mounted. The two sets of signs differ, so a gait from the simulation can move a real leg the wrong way. We added a command that moves each servo on its own, so every direction can be checked one by one.

Managed by testing

Tipping over in Gazebo

The robot falls over in Gazebo, even with a gait that works in PyBullet. We have not found the cause yet, and Gazebo stays experimental.
